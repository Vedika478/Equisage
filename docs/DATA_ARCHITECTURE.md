# Data Architecture

## 1. Overview
The data architecture enforces a strict separation between raw sources, normalized deterministic data, and probabilistic LLM outputs. It tracks the exact lineage of every fact used in the system.

## 2. Decision: Evidence Store (PostgreSQL)

**PostgreSQL is the durable system of record and the authoritative Evidence Store for EquiSage.**
Redis may be introduced later for caching, queues, rate limiting, or temporary job state, but it must NOT be the authoritative evidence store.

**Why PostgreSQL?**
- Provides strict relational integrity needed to map Claims → Metrics → Evidence → Sources.
- ACID guarantees ensure that financial snapshots and point-in-time thesis versions are written atomically.
- `JSONB` support allows storing raw, unstructured API payloads (like filings or deep JSON trees) natively alongside relational metadata.

**Entities Stored in PostgreSQL (Relational):**
- **Sources**: Registries of approved URLs, API endpoints, and quality tiers.
- **Entities/Companies**: Master mapping of symbols (e.g., `RELIANCE.NS`), sectors, and peer groupings.
- **Evidence**: Normalized data points extracted from sources.
- **Metrics**: Outputs from the Deterministic Research Engine.
- **Claims**: Individual AI-generated statements linking to Evidence/Metrics.
- **Theses**: Versioned dossiers, tracking which AI model generated them and the exact Evidence payload used.
- **Critic Findings**: Verification logs detailing why a draft passed or failed.

**Entities Stored in Blob/JSONB:**
- **Raw Source Records**: The exact, untouched JSON/XML returned by an API or scraped from a filing at a specific timestamp. Stored immutably for audit and point-in-time reconstruction.

**Indexing and Search Strategy:**
- **B-Tree Indexes**: Used for exact, high-speed lookups on symbols, timestamps, and foreign keys.
- **GIN Indexes**: Used on `JSONB` columns to quickly query within raw source payloads.
- *(Future)* **pgvector**: Will be utilized if similarity search or RAG is required over extensive unstructured documents.

## 3. Core Layers

### Source Registry
A deterministic registry defining approved, authoritative data sources (e.g., `yfinance`, `nse_india`, `rbi_official`). LLMs cannot invent new sources.

### Raw Source Records
(Stored in PostgreSQL JSONB). The immutable snapshot of the data exactly as it was received.

### Normalized Evidence
Raw data mapped into strict internal schemas (e.g., `FinancialsData`, `PriceData`). 

### Calculated Metrics
Deterministic outputs derived purely from Normalized Evidence via the **Deterministic Research Engine**.

### Claims & Theses
Discrete factual statements generated by the **AI Analyst**. Every claim must hold a foreign key pointer to the specific Normalized Evidence or Calculated Metric that supports it. A Thesis is a versioned collection of Claims forming the **Investment Dossier**.

## 4. Provenance and Lineage

Provenance is strictly enforced at the database level.
- A `Claim` row has a foreign key to a `Metric` or `Evidence` row.
- An `Evidence` row has a foreign key to a `Raw Source Record`.
- A `Raw Source Record` has a foreign key to a `Source Registry` entry.
This unbreakable chain guarantees that the frontend can visually trace any sentence in the Investment Dossier directly back to a specific URL and fetch timestamp.

## 5. Data Quality & Metadata

Every data node must contain:
- **Timestamps**: `fetched_at`, `published_at`, `valid_until`.
- **Source Quality**: Explicit tiering.
- **Freshness**: Rules defining when data is stale. Stale data is explicitly passed to the LLM with a `STALE` flag, never failing silently or updating via hallucination.

## 6. Reconciliation & Conflicts
If two sources disagree on a factual number, the **Deterministic Research Engine** does NOT average them or guess. It persists both to the Evidence Store flagged as `CONFLICTING`, forcing the **AI Analyst** to explicitly address the discrepancy in its report.
